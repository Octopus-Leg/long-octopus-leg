# 9. 웹서비스 배포하기

## 1️⃣ 컨테이너란 무엇인가?
- **컨테이너화의 장점**
  - 애플리케이션에 필요한 모든 **의존성** 및 파일을 하나로 `번들링`하고 설정하여 래핑함.
  - 생성된 번들은 **컨테이너화 프로세스**를 지원하는 모든 시스템에서 실행 가능하며, 어떤 환경에서도 **동일하게 동작**함.
  - 잘못된 설정이나 **의존성 관련 버그를 방지**하고 **배포 시간**을 단축할 수 있음.
  - 컨테이너는 물리적인 시스템과 운영 체제 위에서 동작하며, **운영체제의 커널**을 공유하기 때문에 매우 가벼움.
- **가상화**
  - 컨테이너화와는 서로 다른 개념임.
  - 기존의 하드웨어 시스템을 여러 부분으로 분할하여 가상 환경을 만드는 프로세스이며, 각 부분은 독립적인 `가상 머신(VM)`으로 작동함.
- **컨테이너화와 가상화의 차이점**
  - `가상 머신`은 호스트 시스템 위에 생성되는 반면, `컨테이너`는 하드웨어와 OS 위에서 **격리된 프로세스**로 실행됨.
  - 가상 머신은 **수 GB**에 달할 정도로 무겁지만 컨테이너는 **MB ~ 1GB** 내외의 크기로 매우 가벼움.
  - 컨테이너가 가상 머신보다 **실행 속도**가 빠르며 **이식성** 또한 높음.

## 2️⃣ 도커 이미지 빌드하기

### 도커란 무엇인가?
- 프로세스 식별자(PID), 네트워크(NET), 프로세스 간 통신(IPC), 마운트 포인트(MNT), 유닉스 시간 공유(UTS) 등의 의존성을 패키징해서 높은 `이식성`을 지원함.
- 뛰어난 이식성 덕분에 다양한 환경으로 애플리케이션을 **쉽게 배포**할 수 있음.

#### 도커 아키텍처에 대한 이해
- `클라이언트-서버 아키텍처`를 채택하며, 클라이언트와 **도커 데몬(서버)** 은 `소켓`이나 `RESTful API`를 통해 통신함.
- **도커 클라이언트**는 사용자가 사용하는 `명령줄 인터페이스(CLI)`임.
- **도커 데몬(서버)** 는 컨테이너를 빌드, 실행 및 배포하는 **실제 작업을 수행**함.
- **도커 레지스트리** 는 도커 이미지를 업로드하거나 다운로드할 수 있는 `이미지 리포지토리`임.
- **이미지**는 애플리케이션 실행에 필요한 모든 것이 담긴 **읽기 전용 템플릿**임.
- **컨테이너**는 이미지로부터 생성되어 실제로 실행되는 **인스턴스**임.

#### 도커 컨테이너의 생명주기
| 구분 | 명령어 | 구분 | 명령어 |
| :--- | :--- | :--- | :--- |
| **컨테이너 생성** | `docker create` | **컨테이너 실행** | `docker run` |
| **컨테이너 시작** | `docker start` | **컨테이너 중지** | `docker stop` |
| **일시 중지** | `docker pause` | **일시 중지 해제** | `docker unpause` |
| **재시작** | `docker restart` | **강제 종료** | `docker kill` |
| **컨테이너 제거** | `docker rm` | | |

#### 액추에이터(Actuator) 의존성 추가를 통해 이미지 빌드하기
- build.gradle에 액추에이터 의존성을 추가함.
  - `runtimeOnly 'org.springframework.boot:spring-boot-starter-actuator'`
- `SecurityConfig`에서 액추에이터 엔드포인트에 대해 `.permitAll()` 설정을 적용함.
- **인증 및 권한 부여 여부**와 상관없이 액추에이터 엔드포인트에 접근할 수 있도록 허용함.

#### 스프링 부트 플러그인 태스트 설정하기
- **스프링 부트 그래들 플러그인**은 도커 이미지 빌드를 위한 `bootBuildImage` 명령어를 제공함.
- `build.gradle` 파일에 아래 설정을 추가하여 빌드 옵션을 지정함.
  ```gradle
  bootBuildImage {
      imageName = "192.168.1.2:5000/${project.name}:${project.version}"
  }
  ```
  - 위 설정은 빌드된 이미지가 저장될 로컬 도커 레지스트리의 IP 주소와 포트, 그리고 이미지 이름을 정의함.
  - 이미지 태그에 사용되는 프로젝트 버전은 `build.gradle`에서, 프로젝트 이름은 `settings.gradle`에서 자동으로 가져옴.
  - 프로젝트 이름은 소문자로만 지정해야 오류를 방지할 수 있음.

#### 도커 레지스트리의 설정
- 이미지가 빌드되면 도커 허브의 로그인 자격 증명을 사용해 도커 허브에 푸시할 수 있지만 개발 단계에서는 바람직하지 않음.
- 개발 단계에서는 **로컬 도커 레지스트리**를 구성하여 쿠버네티스 배포 환경과 연동하는 것이 효율적임.
- **로컬 도커 레지스트리 실행 명령어**
  ```bash
  docker run -d -p 5000:5000 -e REGISTRY_STORAGE_DELETE_ENABLED=true --restart=always --name registry registry:2
  ```
  - `-e REGISTRY_STORAGE_DELETE_ENABLED=true`: 이미지 삭제 권한을 부여하는 **환경 변수**를 설정함.
  - `-p 5000:5000`: `호스트 포트:컨테이너 포트`를 연결하여 외부 접속 경로를 확보함.
- 쿠버네티스 환경에서는 레지스트리 호스트를 제공해야 하기 때문에 localhost 대신 **IP 주소나 적절한 호스트 이름을 사용**해야 함.
- 현재 레지스트리는 TLS를 구성하지 않아서 이 레지스트리를 사용하려면 `/etc/docker/daemon.json`에 `insecure-registries` 항목으로 해당 주소를 추가해야 함.

### 이미지를 빌드하는 그래들 태스크 실행
- **Paketo 빌드팩 기반 빌드**
  - `bootBuildImage` 태스크는 **Paketo 빌드팩**을 사용하여 표준화된 도커 이미지를 빌드함.
- **JVM 버전 설정 및 관리**
  - `environment = ["BP_JVM_VERSION" : "17"]` 설정을 통해 이미지 내 Java 버전을 지정함.
  - `Dockerfile`에 JDK 설치 과정을 직접 기술하는 대신, `build.gradle`에서 **선언적으로 런타임 버전을 관리**함.
- **빌드 및 실행 프로세스**
  ```bash
  # 1. 프로젝트 초기화 및 빌드
  ./gradlew clean build
  # 2. 도커 이미지 생성
  ./gradlew bootBuildImage
  # 3. 컨테이너 실행
  docker run -p 8080:8080 192.168.1.2:5000/packt-modern-api-development-chapter09:0.0.1-SNAPSHOT
  # 4. curl 명령어로 사용 가능한 액추에이터 엔드포인트 확인
  curl localhost:8080/actuator
  ```

## 3️⃣ 쿠버네티스에 애플리케이션 배포하기
- **쿠버네티스**
  - 여러 도커 컨테이너를 실행, 관리 및 동적으로 확장할 수 있는 오케스트레이션 도구임.
  - 로컬 환경에서는 **미니큐브(Minikube)** 를 사용하여 쿠버네티스 클러스터를 실행함.
- **미니큐브와 로컬 레지스트리 연동**
  - 미니큐브는 기본적으로 외부 레지스트리를 참조하므로, 로컬 레지스트리 사용 시 비보안 설정이 필요함.
  - `config.json` 내 `InsecureRegistry` 항목에 로컬 레지스트리 IP와 포트를 추가함.
    - `"InsecureRegistry": ["192.168.1.2:5000"]`
  - 실행 시 플래그를 명시함: `minikube start --insecure-registry="192.168.1.2:5000"`
- **네임스페이스(Namespace)**
  - 클러스터 리소스를 사용자나 프로젝트별로 구분하는 논리적 객체이며, 중첩 구조는 불가능함.
- **쿠버네티스 상태 확인 명령어**
  - `kubectl get po -A`: 클러스터 내 모든 파드 상태 확인함.
  - `minikube dashboard`: 대시보드를 통해 시각적으로 리소스 정보 확인함.
- **주요 객체**
  - **Deployment**: 애플리케이션 컨테이너를 실행할 파드의 개수(Replica)와 배포 방식을 정의함.
  - **Service**: 파드의 유동적인 IP를 대신하여 고정된 접근 경로를 제공하는 **추상화 계층**임. 파드가 교체되어도 서비스의 IP/이름은 유지됨.
- **YAML 설정 파일 생성**
  - 쿠버네티스는 YAML 설정을 통해 객체를 생성함.
  ```bash
  # 1. Deployment YAML 생성
  kubectl create deployment chapter09 --image=192.168.1.2:5000/packt-modern-api-development-chapter09:0.0.1-SNAPSHOT --dry-run=client -o=yaml > deployment.yaml
  # 2. 파일 구분선 추가
  echo --- >> deployment.yaml
  # 3. Service YAML 생성 및 추가 (8080 포트 매핑)
  kubectl create service clusterip chapter09 --tcp=8080:8080 --dry-run=client -o=yaml >> deployment.yaml
  ```
- **YAML 파일로 앱을 배포 및 검증**
  ```bash
  # 1. YAML 파일을 이용한 리소스 배포
  kubectl apply -f k8s/deployment.yaml
  # 2. 파드 및 서비스 상태 통합 확인
  kubectl get all
  # 3. 로컬 접근을 위한 포트 포워딩 설정
  kubectl port-forward service/chapter09 8080:8080
  # 4. port-forward를 하면 curl 명령어 사용 가능
  curl localhost:8080/actuator/health
  ```
- **파드**
  - 쿠버네티스의 **가장 작은 객체 단위로 배포가 가능한 객체**임.
  - 여기에는 하나 이상의 컨테이너가 포함되며 쿠버네티스 클러스터에서 실행 중인 단일 인스턴스를 의미함.
  - 쿠버네티스가 파드의 상태를 관리하고 있다가 파드가 다운되면 다른 파드로 대체하기 때문에 **IP 등의 구성 관련 정보는 언제든 변경**될 수 있음.
  - 따라서 쿠버네티스의 service 객체는 내부에 포함된 파드의 IP 주소를 외부에 노출하거나 파드에 대한 맵핑 정보를 관리하는 등의 추상화 계층을 제공함.
