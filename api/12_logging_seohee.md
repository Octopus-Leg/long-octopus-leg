## 12. 서비스에 로깅 및 트레이싱 추가

## 1️⃣ ELK 스택을 활용한 로깅 및 트레이싱
- 마이크로서비스 환경은 여러 프로세스가 분산되어 실행되므로 로그를 한곳으로 모으는 중앙 집중식 로깅이 필수적임.
- 여러 서비스에 걸친 요청 흐름을 추적하기 위해 `트레이싱 식별자(traceId)` 또는 `상관 식별자(correlationId)`를 사용하여 전 구간을 연결하고 관리함.
- 로그는 시스템 에러의 근본 원인을 파악하는 디버깅 도구일 뿐만 아니라 처리량과 시스템 상태를 모니터링하는 핵심 데이터를 제공함.
- 시장에는 Splunk, Graylog, ELK 스택을 포함해서 로깅을 위해 사용할 수 있는 다양한 오픈 소스 또는 엔터프라이즈 도구들이 있음.

### ELK 스택의 이해
- **Elasticsearch**, **Logstash**, **Kibana**라는 세 가지 강력한 오픈 소스 도구가 결합된 플랫폼임.
- 시스템에서 발생하는 다양한 타입의 로그를 실시간으로 집계하고 분석하며 시각적인 모니터링 환경을 구축함.
  1. 서비스/시스템 로그는 TCP 포트의 Logstash로 푸시됨.
  2. Logstash는 인덱싱을 위해 로그를 Elasticsearch로 푸시함.
  3. Kibana는 Elasticsearch 인덱스를 사용해 로그를 쿼리하고 시각화함.
  > 💡 이 외에도 서비스 로그와 Logstash 사이에 Redis, Kafka, RabbitMQ 같은 브로커 계층을 넣어 데이터 손실을 방지하고 데이터 급증 상황에도 대비할 수 있음.

#### 엘라스틱서치
- **아파치 루씬**을 기반으로 자바로 개발된 고성능의 **텍스트** 검색 엔진이며, 대규모 데이터를 빠르게 처리하는 엔터프라이즈급 성능을 가짐.
- 엘라스틱서치는 분산 배포가 가능하고 다중 테넌시를 지원함. 또한 클러스터링을 지원하는 분산 검색 엔진임.
  - **다중 테넌시**란, 하나의 엘라스틱서치 클러스터 내에서 여러 개의 독립된 인덱스(데이터 저장 단위)를 생성하고 관리하며 서로 다른 서비스의 로그를 분리해 검색할 수 있는 기능을 의미함.
- 클러스터 확장이 용이하고 약 1초 내외의 지연 시간만 발생하는 거의 실시간 검색 기능을 지원함.
- 데이터 모델은 JSON으로 나타내고 **JSON 기반의 스키마 없는 스토리지**를 제공하며, HTTP 요청과 응답에서 JSON 다큐먼트를 사용함.

#### 로그스태시
- 다양한 소스로부터 로그를 수집하여 가공한 뒤 목적지로 전송하는 **실시간 파이프라인 데이터 수집 엔진**임.
- 로그스태시는 데이터를 수집하고, 구문을 분석하고, 필터링하고, 엘라스틱서치와 같은 지정된 데이터 저장소 또는 콘솔의 단순 표준 출력으로 전송하는 에이전트로 실행됨.
- 이 외에도 다양한 플러그인 세트가 있음.

#### 키바나
- 키바나는 데이터를 **분석하고 시각화**하기 위해 사용되는 전용 **웹 애플리케이션**임.
- 엘라스틱서치와 상호 작용이 편리하며 손쉬운 통합을 제공함. 엘라스틱서치 인덱스에 저장된 정보를 검색, 표시하고 상호 작용할 수 있음.
- 키바나는 고급 데이터 분석을 수행하고 다양한 차트, 테이블, 지도에서 데이터를 시각화할 수 있는 브라우저 기반 웹 응용 프로그램임.
- 별도의 설정이나 코딩, 추가 인프라가 필요하지 않음.


## 2️⃣ ELK 스택 설치
- 환경에 구애받지 않는 일관된 배포를 위해 `YAML` 설정 파일을 사용하는 **도커 컴포즈**로 스택을 구성함.
- 도커 컴포즈의 `version`, `services`, `networks`, `volumes` 키워드를 사용하여 컨테이너의 실행 환경과 데이터 보존 방식을 정의함.
- **elasticsearch** 서비스에 컨테이너 이름, 도커 이미지, 환경 변수, 네트워크를 정의하고 **외부:내부** 형식으로 포트도 정의함.
  - 포트는 `19200:9200`으로 정의하며, 브라우저에서는 포트 `19200`으로 액세스하고 다른 서비스는 엘라스틱서치와 통신하기 위해 `9200`을 사용함.
- **logstash** 서비스는 실행 명령인 `command`에 **TCP 5001**번 포트로 **JSON** 로그를 수신하도록 직접 설정을 주입하고, `depends_on`으로 엘라스틱서치를 먼저 시작하도록 지시함.
- **kibana** 서비스는 `ELASTICSEARCH_HOSTS=http://es-container:9200` 환경 변수를 사용하여 엘라스틱서치 컨테이너와 내부적으로 통신하도록 설정함.
- `docker-compose up -d` 명령으로 전체 서비스를 백그라운드에서 실행하며, `depends_on`을 통해 엘라스틱서치가 구동된 후 나머지 서비스가 실행되도록 제어함.
- 도커 컴포즈는 네트워크를 만든 다음 서비스 컨테이너를 생성하고 시작함.
- 모든 컨테이너가 기동되면 브라우저에서 `http://localhost:19200/` 에 접속해서 엘라스틱서치 인스턴스가 작동 중인지 확인하고, `http://localhost:5600/` 에 접속해 키바나 대시보드를 확인할 수 있음.
- 로그를 보는 명령어는 `docker-compose logs [서비스이름]`, 도커 컴포즈를 종료하는 명령어는 `docker-compose down`임.
> 엘라스틱서치는 기본적으로 많은 메모리를 점유하므로, 도커 설정에서 최소 **8 GB** 이상의 메모리를 할당해야 **error-137**과 같은 실행 중 중단 에러를 방지할 수 있음.


## 3️⃣ gRPC 코드에서 로깅 및 트레이싱 구현
- 스프링 부트 3 이전에는 `Spring Cloud Sleuth` 라이브러리를 사용했으나, 스프링 부트 3부터는 **Spring Micrometer**가 트레이싱을 공식 지원함.
- 분산 트랜잭션의 시작부터 끝까지 동일하게 유지되는 `traceId`와 개별 작업 단위인 `spanId`를 정의하여 복잡한 서비스 간 호출 흐름을 구조화함.
- 책의 프로젝트에서는 Zipkin의 분산 추적 라이브러리인 **Brave**를 활용하여 트레이싱 정보를 생성하고 서비스 간에 전파함.

### gRPC 서버 코드 변경
- `build.gradle`에 `logstash-logback-encoder`, `micrometer-tracing-bridge-brave`, `spring-boot-starter-actuator` 의존성을 추가하여 로깅 및 트레이싱 환경을 준비함.
- `logback-spring.xml` 설정 파일에 `LogstashTcpSocketAppender`를 추가하여 로그를 로그스태시로 전송하며, **INFO** 레벨의 정보성 로그만 출력하도록 구성함.
- `application.properties` 파일을 수정하여 로그스태시 대상 호스트를 지정하고, 트레이싱을 위한 샘플링 비율(`management.tracing.sampling.probability`)을 **1.0**으로 설정하여 모든 요청을 100% 수집함.
- `ObservationGrpcServerInterceptor`를 스프링 빈으로 등록한 뒤, gRPC 서버 빌더의 인터셉터 설정에 추가하여 요청 수신 시 자동 트레이싱이 활성화되도록 구현함.

### gRPC 클라이언트 코드 변경
- 클라이언트 프로젝트에도 서버와 동일한 의존성을 `build.gradle`에 추가하여 트레이싱 기능을 활성화함.
- `logback-spring.xml` 설정 파일도 서버와 동일한 방식을 적용하여 로그가 중앙 집중식으로 수집되도록 함.
- `application.properties` 파일을 통해 로그스태시 목적지를 설정하고, 서버와 마찬가지로 샘플링 비율을 **1.0**으로 유지함.
- gRPC 채널 생성 시 클라이언트 전용 인터셉터인 `ObservationGrpcClientInterceptor`를 주입하여, 서버로 요청을 보낼 때 트레이싱 컨텍스트가 헤더를 통해 전파되도록 구현함.

### 로깅 및 트레이싱 변경사항 테스트
- ELK 스택 컨테이너와 애플리케이션 서비스를 모두 실행한 뒤, `curl` 명령으로 REST 엔드포인트를 호출하여 실제 gRPC 통신을 발생시킴.
- 생성된 로그의 패턴을 확인했을 때 클라이언트와 서버 양쪽 로그 블록에서 동일한 `traceId`가 출력되는 것을 통해 트레이싱 상태를 확인함.
- 키바나의 **Discover** 메뉴에서 인덱스 패턴(`modern-api`)을 생성한 뒤, **KQL** 쿼리를 사용하여 특정 `traceId`와 관련된 모든 서비스의 로그를 한눈에 필터링하여 분석함.


## 4️⃣ Zipkin과 Micrometer로 분산 트레이싱 하기
- **Spring Micrometer**는 벤더-중립적인 API를 제공하며 JVM, CPU, 레이턴시 등 다양한 성능 메트릭을 수집하여 여러 모니터링 도구와 유연하게 연동함.
- 텍스트 기반의 로그 분석보다 서비스 간의 구체적인 **호출 시간**과 **지연 시간** 분석이 필요한 경우 **Zipkin** 시각화 도구가 매우 효과적임.

- **1. Zipkin 설정 및 실행**
  - `build.gradle`에 `zipkin-reporter-brave` 의존성을 추가하여 수집된 트레이싱 정보를 Zipkin 서버로 전송할 준비를 함.
  - `application.properties` 파일에서 Zipkin API 엔드포인트 주소를 지정하여 데이터 전송 경로를 설정함.
  - 별도의 설치 과정 없이 독립 실행형 JAR 파일을 실행하여 기본적으로 **9411** 포트에서 작동하는 Zipkin 대시보드를 구동함.

- **2. 트레이싱 데이터 확인**
  - 로그를 통해 파악한 특정 `traceId`를 Zipkin UI 검색창에 입력하여 전체 서비스 호출 계층 구조를 시각적으로 확인함.
  - 각 구간별 소요 시간을 그래프로 파악하여 어떤 서비스나 구간에서 성능 병목이 발생하는지 확인할 수 있음.
  - 상세 정보의 **Annotations** 탭을 통해 개별 호출의 정확한 시작과 종료 시점을 확인할 수 있음.
