# 13.GraphQL 시작하기

## 1️⃣ GraphQL 알아보기
- **GraphQL**은 선언적 쿼리이자 API용 조작 언어이며 서버-사이드 런타임임.
- 클라이언트가 원하는 데이터를 정확하게 쿼리할 수 있도록 지원함.
### GraphQL의 간략한 역사
- 2011년 **메타(페이스북)** 에서 모바일 웹사이트 성능 개선을 위해 개발을 시작함.
- 당시 네트워크 속도가 느린 환경에서 계층적이고 재귀적인 데이터를 최적화하기 위해 고안됨.
- 2012년 내부적으로 완성되어 사용되었고, 2015년에 **오픈 소스**로 대중에 공개됨.
### GraphQL과 REST 비교
- REST는 고정된 구조의 엔드포인트를 사용하여 필요한 정보를 얻기 위해 여러 번의 호출이 발생할 수 있음.
- **GraphQL**은 단 하나의 엔드포인트만 노출하며, 한 번의 호출로 여러 데이터를 동시에 가져올 수 있어 네트워크 호출 횟수를 줄임.
- 요청 시 응답받고 싶은 필드를 직접 기술할 수 있어 **오버/언더페칭** 문제를 방지해서 네트워크 대역폭을 효과적으로 사용함.
- REST는 내장 HTTP 명세를 사용해 캐싱을 제공하지만 GraphQL은 Apollo/Relay와 같은 라이브러리를 사용해 캐시함.
- GraphQL은 모바일 클라이언트에서 사용될 때 REST API보다 우수함.
- **SDL(스키마 정의 언어)** 을 사용하여 강력한 타입을 정의하며, 이는 서버와 클라이언트 간의 계약 역할을 수행함.

## 2️⃣ GraphQL 기초 학습
- **GraphQL API**는 세 가지 주요 루트 타입인 **쿼리**, **뮤테이션**, **서브스크립션**을 가짐.
- 모든 요청은 단일 엔드포인트를 통해 `JSON` 응답을 반환함.
### 쿼리 타입 살펴보기
- 서버에서 정보를 가져오는 **읽기 작업**에 사용됨.
- `type Query` 내에 실행 가능한 쿼리 루트를 정의하고, 객체 타입을 통해 필드와 반환 타입을 지정함.
- **익명 쿼리**: `query` 접두사를 생략할 수 있으며, 이 경우 디폴트로 쿼리로 동작함.
- 요청 페이로드는 중괄호(`{}`)로 묶으며, 주석은 `#`을 사용함.
### 뮤테이션 타입 살펴보기
- 서버에서 수행되는 추가, 업데이트, 삭제와 같은 **쓰기 작업**에 사용됨.
- GraphQL 요청 입력이 `mutation` 키워드로 시작해야 하며, 그렇지 않으면 쿼리로 처리되어 에러가 발생할 수 있음.
- **아규먼트**: 필요한 매개변수는 `()` 괄호로 묶어 전달하며, `!` 표시는 **nullable이 아닌 값**을 의미하고, 리스트는 `[]`로 표시함.
- `Int`는 부호가 있는 32비트 정수형 내장 스카라 타입이며, 디폴트 값은 `null`임.
### 서브스크립션 타입 살펴보기
- 실시간 업데이트가 필요한 경우 사용되는 기술로, 클라이언트가 이벤트를 구독하면 서버가 스트림을 통해 데이터를 푸시함.
- **웹소켓(WebSocket)** 등을 사용하여 안정적인 연결을 유지하며 실시간 점수 업데이트나 일괄 처리 업데이트에 권장됨.
- 큰 객체의 작은 업데이트가 발생하거나 대기 시간이 짧은 라이브 업데이트가 필요한 경우에 적합함.


## 3️⃣ GraphQL 스키마 설계
- 스키마는 **DSL** 구문을 사용하여 작성하는 `.graphql` 파일임.
- 루트 타입(쿼리, 뮤테이션, 서브스크립션)과 객체 타입, 스칼라 타입, 인터페이스, 유니온, 인풋 타입 등으로 구성됨.
### 스칼라 타입의 이해
- **스칼라 타입**은 구체적인 데이터를 확인하며, GraphQL은 5가지 내장 타입을 제공함.
    - `Int`: 부호 있는 32비트 정수.
    - `Float`: 부호 있는 배정밀도 부동 소수점.
    - `String`: UTF-8 문자열.
    - `Boolean`: `true` 또는 `false`.
    - `ID`: 객체 식별자 문자열로, 직렬화 시 문자열로 처리됨.
- **커스텀 스칼라**: `scalar Date`와 같이 고유한 타입을 정의할 수 있으며, 직렬화 및 유효성 검사 로직 구현이 필요함.
- **열거형 타입(enum)**: `enum OrderStatus`와 같이 허용되는 값의 특정 세트를 정의함.
### 프래그먼트 이해
- **별칭(alias)**: 동일한 객체를 다른 인자로 여러 번 요청할 때 발생하는 충돌을 피하기 위해 쿼리 결과에 이름을 지정함.
- **프래그먼트**: 쿼리에서 재사용 가능한 필드 집합을 논리적으로 그룹화함.
- **인라인 프래그먼트**: 명시적으로 선언하지 않고 쿼리 내에서 즉석 생성하며, 인터페이스나 유니온 타입을 리턴할 때 유용함.
### 인터페이스 이해
- **인터페이스**는 여러 객체 타입에 공통적인 필드 세트를 정의하는 추상 타입임.
- `interface Product`를 정의하고 `type Book implements Product`와 같이 구현함.
- 클라이언트 쿼리 시 인라인 프래그먼트(`··· on Book`)를 사용하여 구현체별 특정 필드를 요청할 수 있음.
### 유니온 타입의 이해
- **유니온 타입**은 공통 필드가 없는 두 개 이상의 객체 타입을 하나의 필드에서 반환할 때 사용함.
- `union SearchResult = Book | Author`와 같이 파이프(`|`) 기호로 구분함.
- 응답에서 `__typename` 필드를 통해 반환된 객체의 실제 타입을 구별할 수 있음.
### 인풋 타입의 이해
- **인풋 타입**은 뮤테이션에서 객체 전체를 아규먼트로 전달할 때 사용함.
- `type` 대신 `input` 키워드로 선언하며, 클라이언트에서 `Variable` 영역에 JSON 객체를 매핑하여 전달함.
### GraphQL 도구를 사용한 스키마 설계
- **GraphiQL**: 웹 기반의 공식 통합 개발 환경(IDE)으로 인터랙티브한 쿼리 작성을 지원함.
- **GraphQL Playground**: 인기 있었던 IDE로 현재는 GraphiQL에 통합되거나 유지보수 상태임.
- **GraphQL Faker**: 테스트를 위한 모의 데이터를 제공함.
- **GraphQL Editor**: 스키마를 시각적으로 디자인하고 코드로 변환함.
- **GraphQL Voyager**: 스키마를 엔티티 다이어그램 형태의 상호작용 그래프로 시각화함.

## 5️⃣ N+1 문제 해결
- **N+1 문제**는 연관 관계가 있는 엔티티를 조회할 때, 의도하지 않은 추가 쿼리가 반복적으로 실행되어 성능을 저하시키는 현상임.
- 자바 개발자에게 익숙한 문제이며, 하이버네이트를 사용할 때, 쿼리를 최적화하지 않았거나 엔터티를 올바르게 작성하지 않으면 발생할 수 있는 문제임.
### N+1 문제 이해란 무엇인가?
- User과 Order 사이의 일대다 관계를 예로 들면 다음과 같음.
- 1. 모든 사용자를 찾는 쿼리가 1번 실행됨(1번).
- 2. 결과로 반환된 각 사용자(N명)에 대해 주문 목록을 가져오는 쿼리가 각각 실행됨(N번).
- 결과적으로 1번의 조회를 위해 총 **N+1번**의 SQL 문이 실행되어 네트워크 및 데이터베이스 부하가 증가함.
### GraphQL에서 N+1 문제가 발생하는 이유
- GraphQL의 **리졸버** 작동 방식 때문임.
- GraphQL 서버의 각 필드는 자체적인 리졸버 기능을 가지며 독립적으로 실행됨.
- `getUsersOrders` 쿼리 실행 시, 첫 번째 리졸버가 모든 사용자를 가져오고, 이어지는 `orders` 필드 리졸버가 각 사용자 ID를 기반으로 주문 정보를 별도로 호출함.
- 따라서 `orders` 리졸버는 n번 실행됨.
- 필드 단위로 데이터를 가져오는 GraphQL의 유연한 구조가 데이터베이스 최적화 관점에서는 비효율적인 반복 쿼리를 유발함.
### N+1 문제의 솔루션
- **배치** 처리를 통해 모든 사용자의 주문 정보를 한 번의 쿼리로 모아서 가져오는 해결책이 필요함.
- **DataLoader 라이브러리**: GraphQL에서 제공하는 라이브러리로, 개별 요청을 수집했다가 한 번의 데이터 저장소 호출로 처리함.
- 자바 환경에서는 `java-dataloader` 라이브러리를 사용하여 유사한 기능을 구현할 수 있음.
- 이를 통해 리졸버가 N번 반복 호출되는 대신, 단일 또는 최소한의 쿼리로 모든 레코드를 수신할 수 있게 됨.
