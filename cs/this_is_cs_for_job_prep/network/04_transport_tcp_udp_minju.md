## 4. 전송 계층 - TCP와 UDP

### TCP와 UDP의 목적과 특징

패킷의 최종 송수신 대상은 호스트가 아니라 **호스트가 실행하는 프로세스**임. 프로세스는 **포트** 번호를 통해 식별할 수 있으며, IP 주소와 포트 번호의 조합으로 특정 호스트의 특정 프로세스를 식별함 (예: `192.168.0.15:8000`).

#### 포트를 통한 프로세스 식별

포트를 통한 프로세스 식별은 전송 계층(TCP, UDP)의 주된 목적임. TCP와 UDP 헤더 모두 **송신지 포트 번호**와 **수신지 포트 번호** 필드를 포함함.

- 포트 번호는 16비트로 표현되어 총 2¹⁶ = 65536개(0번 ~ 65535번)임. 범위에 따라 3가지로 나뉨.
- 서버 프로그램은 주로 잘 알려진/등록된 포트가 할당되고, 클라이언트 프로그램(예: 웹 브라우저)은 동적 포트 중 임의 번호가 자동 할당됨.

| 포트 종류 | 포트 번호 범위 | 설명 |
|---|---|---|
| **잘 알려진 포트(well-known port)** | 0 ~ 1023 | 가장 대중적으로 사용되는 애플리케이션을 위한 포트 번호 |
| **등록된 포트(registered port)** | 1024 ~ 49151 | 흔하게 사용되는 애플리케이션 프로토콜에 할당하는 포트 번호 |
| **동적 포트(dynamic port)** | 49152 ~ 65535 | 사설(private)/임시(ephemeral) 포트. 비교적 자유롭게 사용 가능한 포트 번호 |

| 잘 알려진 포트 번호 | 프로토콜 |
|---|---|
| 20, 21 | FTP |
| 22 | SSH |
| 23 | TELNET |
| 53 | DNS |
| 67, 68 | DHCP |
| 80 | HTTP |
| 443 | HTTPS |

| 등록된 포트 번호 | 용도 |
|---|---|
| 1194 | OpenVPN |
| 1433 | Microsoft SQL Server 데이터베이스 |
| 3306 | MySQL 데이터베이스 |
| 6379 | Redis |
| 8080 | HTTP 대체 |

> 공인 IP 주소와 사설 IP 주소 간 변환에 사용하는 기술이 **NAT(Network Address Translation)** 임. 사설 네트워크의 호스트가 외부와 통신하려면 변환이 필요하며, 대부분의 라우터/공유기가 NAT 기능을 내장함.<br>
> 다수의 사설 IP 주소를 적은 수의 공인 IP 주소로 변환할 때, IP 주소 쌍과 함께 **포트 번호**도 고려하는 포트 기반 NAT를 **NAPT(Network Address Port Translation)** 라고 함. 같은 공인 IP로 변환되더라도 포트 번호로 내부 호스트를 구분함.

#### (비)신뢰성과 (비)연결형 보장

| 프로토콜 | 신뢰성 | 연결 | 제공 기능 |
|---|---|---|---|
| **TCP** | 신뢰할 수 있음 | 연결형 | 연결 수립·종료 과정O, 상태 관리, 흐름 제어, 오류 제어, 혼잡 제어 등 신뢰성 보장 기능 제공O |
| **UDP** | 신뢰할 수 없음 | 비연결형 | 연결 수립·종료 과정X, 신뢰성 보장 기능 제공X |

- 신뢰할 수 있는 연결형 송수신에는 시간과 연산이 소요되어 TCP는 UDP보다 송수신 속도가 느림.
- 패킷의 유실 없는 송수신을 원하면 TCP, 비교적 빠른 송수신을 원하면 UDP가 유리함.

**UDP 헤더**: 송신지 포트, 수신지 포트, **길이**(헤더 포함 UDP 패킷의 데이터그램의 바이트 크기), **체크섬**(송수진 과정에서 데이터그램 훼손 여부) 필드로 구성됨. 사실상 IP 헤더를 감싸는 헤더와 같음.

**TCP 헤더**: UDP보다 필드가 훨씬 많음. 우선적으로 알아야 하는 필드는 3가지임.
- **순서 번호(sequence number)** : TCP 세그먼트의 올바른 송수신 순서를 보장하기 위해 세그먼트 첫 바이트에 매겨진 번호
- **확인 응답 번호(acknowledgment number)** : 상대 호스트가 보낸 세그먼트에 대한 응답으로, 다음으로 수신하길 기대하는 순서 번호. 일반적으로 '올바르게 수신한 순서 번호 + 1'로 설정됨.
- **제어 비트(control bit, 플래그 비트)** : 세그먼트에 대한 부가 정보. 8비트로 구성됨.

| 제어 비트 | 의미 |
|---|---|
| **ACK** | 세그먼트의 승인을 나타내기 위한 비트 |
| **SYN** | 연결을 수립하기 위한 비트 |
| **FIN** | 연결을 종료하기 위한 비트 |

### TCP의 연결부터 종료까지

#### TCP의 연결 수립

TCP 연결 수립은 **쓰리 웨이 핸드셰이크(three-way handshake)** 를 통해 세 단계로 이루어짐.

**호스트 A가 호스트 B에게 처음 연결 요청을 보내는 과정**

| 단계 | 송수신 방향 | 세그먼트 | 내용 |
|---|---|---|---|
| ① | A → B | SYN | SYN 비트 1로 설정. 호스트 A의 순서 번호 포함 |
| ② | B → A | SYN + ACK | ACK와 SYN 비트 1로 설정. B의 순서 번호 + A에 대한 확인 응답 번호 포함 |
| ③ | A → B | ACK | ACK 비트 1로 설정. A의 순서 번호 + B에 대한 확인 응답 번호 포함 |

- 처음 연결을 시작하는 과정을 **액티브 오픈(active open)** , 연결 요청을 수신한 뒤 수립하는 과정을 **패시브 오픈(passive open)** 이라고 함.
- 서버-클라이언트 관계에서 액티브 오픈은 주로 클라이언트, 패시브 오픈은 주로 서버가 수행함.

#### TCP의 오류·흐름·혼잡 제어

TCP는 패킷의 신뢰성 보장을 위해 3가지 기능을 제공함.

**① 재전송을 통한 오류 제어**: 잘못 전송된 세그먼트를 재전송함.

**잘못 전송된 세그먼트를 인지하는 상황**

- **중복된 ACK 세그먼트 수신하는 상황**: 송신한 세그먼트 일부가 유실되어 같은 ACK를 중복 수신
- **타임아웃이 발생한 상황**: 세그먼트 전송 시 시작한 **재전송 타이머**의 카운트다운이 끝날 때까지 ACK를 받지 못하면 재전송

**② 흐름 제어(flow control)** : 수신 호스트가 한 번에 받아 처리할 수 있을 만큼만 전송하는 것. 송신 호스트와 수신 호스트의 송수신 처리 속도를 맞춤.

- 수신 호스트가 받을 수 있는 전송량은 TCP 수신 버퍼 크기에 의해 결정됨.
- TCP 헤더의 **윈도우(window)** 필드에 **수신 윈도우** 크기가 명시되어, 수신 호스트가 한 번에 처리 가능한 양을 송신 호스트에 알림.

**③ 혼잡 제어(congestion control)** : 많은 트래픽으로 패킷 처리가 느려지거나 유실될 수 있는 혼잡을 제어하는 기능. 주체는 **송신 호스트**임.

- 혼잡 판단 기준은 세그먼트 전송 오류 판단과 같음. (중복 ACK 수신, 타임아웃)
- 혼잡 없이 전송할 수 있는 양을 **혼잡 윈도우(congestion window)** 라고 함. 수신 윈도우는 수신 호스트가 알려 주지만, 혼잡 윈도우는 송신 호스트가 직접 계산해야 함.
- 혼잡 윈도우 크기를 연산하는 과정을 **혼잡 제어 알고리즘**이라고 함. 가장 기본적인 것이 **AIMD(Additive Increase/Multiplicative Decrease)** 임.
- AIMD: 혼잡이 감지되지 않으면 혼잡 윈도우를 1씩 선형적으로 증가, 혼잡이 감지되면 절반으로 떨어뜨리는 알고리즘. (톱니 모양으로 변화함)

> **RTT(Round Trip Time)** : 패킷을 보내고 그에 대한 응답이 수신되기까지의 시간.<br>
> AIMD는 '혼잡 윈도우를 RTT마다 1씩 선형적 증가, 혼잡 시 절반으로 감소시키는 알고리즘'으로 정의할 수도 있음. `ping` 결과의 `rtt min/avg/max/mdev`가 RTT의 최솟값/평균값/최댓값/표준편차임.

#### TCP의 종료

TCP 연결 종료는 송수신 호스트가 각자 한 번씩 FIN과 ACK를 주고받으며 이루어지므로 **포 웨이 핸드셰이크(four-way handshake)** 라고도 부름.

| 단계 | 송수신 방향 | 세그먼트 |
|---|---|---|
| ① | A → B | FIN |
| ② | B → A | ACK |
| ③ | B → A | FIN |
| ④ | A → B | ACK |

- 먼저 연결을 종료하려는 호스트의 동작을 **액티브 클로즈(active close)**, 연결 종료 요청을 받아들이는 호스트의 동작을 **패시브 클로즈(passive close)** 라고 함.

### TCP의 상태 관리

- TCP: **상태(state)** 를 유지하고 관리하는 프로토콜이라는 점에서 **스테이트풀 프로토콜(stateful protocol)** 이라고도 부름.
- 상태: 각종 네트워크 명령어(`netstat` 등)에서 확인할 수 있으며, 송수신 현황 판단이나 디버깅에 활용됨.

**① 연결이 수립되지 않았을 때 주로 활용되는 상태**

| 상태 | 설명 |
|---|---|
| CLOSED | 아무런 연결이 없는 상태 |
| LISTEN | 연결 대기 상태(SYN 세그먼트를 대기하는 상태) |

**② 연결 수립 과정에서 주로 활용되는 상태** (쓰리 웨이 핸드셰이크 기준)

| 상태 | 설명 |
|---|---|
| SYN-SENT | 액티브 오픈 호스트가 SYN을 보낸 뒤 SYN+ACK를 기다리는 상태(연결 요청 전송) |
| SYN-RECEIVED | 패시브 오픈 호스트가 SYN+ACK를 보낸 뒤 ACK를 기다리는 상태(연결 요청 수신) |
| ESTABLISHED | 쓰리 웨이 핸드셰이크가 끝나 데이터를 송수신할 수 있는 상태(연결 수립) |

**③ 연결 종료 과정에서 주로 활용되는 상태**

| 상태 | 설명 |
|---|---|
| FIN-WAIT-1 | 액티브 클로즈 호스트가 FIN 세그먼트로 연결 종료 요청을 보낸 상태(연결 종료 요청 전송) |
| CLOSE-WAIT | FIN 세그먼트를 받은 패시브 클로즈 호스트가 ACK를 보낸 후 대기하는 상태(연결 종료 요청 승인) |
| FIN-WAIT-2 | FIN-WAIT-1 상태에서 ACK 세그먼트를 받은 상태 |
| LAST-ACK | CLOSE-WAIT 상태에서 FIN 세그먼트를 전송한 뒤 대기하는 상태 |
| TIME-WAIT | 액티브 클로즈 호스트가 마지막 ACK를 전송한 뒤 접어드는 상태 |

- 패시브 클로즈 호스트는 마지막 ACK 수신 시 CLOSED가 되지만, TIME-WAIT에 접어든 액티브 클로즈 호스트는 일정 시간 대기 후 CLOSED가 됨. (마지막 ACK 세그먼트가 유실되어 재전송이 필요할 수 있기 때문임.)

> **CLOSING 상태**: 서로가 FIN 세그먼트를 보내고 받은 뒤 각자 ACK를 보냈지만, 아직 자신의 FIN 세그먼트에 대한 ACK 세그먼트를 받지 못했을 때 접어드는 상태<br>
> 양쪽이 동시에 종료를 요청하고 서로의 종료를 기다릴 때 발생함.
