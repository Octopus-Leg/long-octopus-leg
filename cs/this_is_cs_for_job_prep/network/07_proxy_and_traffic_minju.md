## 7. 프록시와 안정적인 트래픽

### 오리진 서버와 중간 서버: 포워드 프록시와 리버스 프록시

실제로는 클라이언트와 서버 사이에 수많은 네트워크 장비와 중간 서버가 있을 수 있으며, 서버를 다중화하여 운영하는 경우도 많음.

- **오리진 서버(origin server)**: 자원을 생성하고 클라이언트에게 권한이 있는 응답을 보낼 수 있는 HTTP 서버. 클라이언트가 최종적으로 메시지를 주고받는 대상임

대표적인 중간 서버 유형은 프록시와 게이트웨이임.

| 유형 | 별칭 | 설명 |
|---|---|---|
| **프록시(proxy)** | 포워드 프록시 | 클라이언트가 선택한 메시지 전달의 대리자. 캐시 저장, 암호화, 접근 제한 등 제공. 클라이언트에 더 가까이 위치 ('클라이언트의 심부름꾼') |
| **게이트웨이(gateway)** | 리버스 프록시 | 오리진 서버(들)로 향하는 요청을 먼저 받아 전달하는 문지기/경비. 클라이언트 시각에서 오리진 서버처럼 보임. 오리진 서버에 더 가까이 위치. 캐시 저장, 로드 밸런서로도 동작 |

### 고가용성: 로드 밸런싱과 스케일링

#### 가용성

**가용성(availability)** 은 특정 컴퓨터 시스템이 주어진 기능을 실제로 수행할 수 있는 시간의 비율임. 이 비율이 높으면 **고가용성(HA, High Availability)** 이라고 함.

```
              업타임
가용성 = ─────────────────
         업타임 + 다운타임
```

- **업타임(uptime)**: 정상 사용 시간 / **다운타임(downtime)**: 정상 사용이 불가능한 시간
- 안정적이라 평가받는 시스템의 가용성은 **99.999%(파이브 나인스)** 이상을 목표로 함. 이는 다운타임이 대략 1년에 5.26분, 1개월에 26.3초임을 의미함.
- 다운타임 원인은 과도한 트래픽, 소프트웨어 오류, 하드웨어 장애, 보안 공격, 자연재해 등 다양함.
- 가용성의 핵심은 '문제가 발생하더라도 계속 기능할 수 있도록' 설계하는 것임. 이 능력을 **결함 감내**라고 하며, 대표 기술이 **다중화**임 (문제 시 다른 예비 서버가 대신 동작).

> **페일오버·헬스 체크·하트비트**: **페일오버(failover)** 는 동작하는 시스템에 문제가 생겼을 때 예비 시스템으로 자동 전환되는 기능임. **헬스 체크(health check)** 는 문제 있는 서버가 있는지 주기적으로 검사하는 것으로, 주로 로드 밸런서에 의해 HTTP·ICMP 등으로 이루어짐. **하트비트(heartbeat)** 는 서버 간 주기적으로 하트비트 메시지를 주고받다가 끊겼을 때 문제를 감지하는 방법임.

#### 로드 밸런싱

과도한 트래픽은 서버의 가용성을 떨어뜨림. 서버를 다중화해도 특정 서버에만 트래픽이 몰리면 가용성이 떨어질 수 있음. 트래픽의 고른 분배를 위한 기술이 **로드 밸런싱(load balancing)** 임.

- **로드 밸런서(load balancer)**: 다중화된 서버와 클라이언트 사이에 위치하며 요청을 각 서버에 균등하게 분배함. L4/L7 스위치라 불리는 네트워크 장비나 소프트웨어(HAProxy, Envoy, Nginx 등)로 수행 가능
**로드 밸런싱 알고리즘**: 부하가 균등하게 분산되도록 요청을 전달할 서버를 선택하는 방법

| 알고리즘 | 설명 |
|---|---|
| **라운드 로빈(round robin)** | 단순히 서버를 돌아가며 부하를 전달 |
| **최소 연결(least connection)** | 연결이 적은 서버부터 우선적으로 부하 전달 |

- 이 외에도 해시 이용, 무작위, 응답 시간이 가장 짧은 서버 선택 등이 있음.
- 모든 서버에 균일한 부하를 부여하는 전략은 모든 서버의 성능이 동일할 때만 유효함. 성능이 다르면 성능이 좋은 서버에 더 많은 트래픽을 분배하도록 **가중치**를 부여할 수 있음. 거의 대부분의 로드 밸런서가 가중치 알고리즘을 지원함.

#### 스케일링: 스케일 업과 스케일 아웃

서버·부품·네트워크 장비 등 인프라를 확장/업그레이드하는 방법은 크게 2가지임.

| 방식 | 다른 이름 | 설명 | 장단점 |
|---|---|---|---|
| **스케일 업(scale up)** | 수직적 확장 | 기존 부품을 더 나은 사양으로 교체 | 설치·구성이 단순하나 유연성이 낮음. 병목·단일 장애 우려 |
| **스케일 아웃(scale out)** | 수평적 확장 | 기존 부품을 여러 개로 둠 | 유연한 확장·축소 가능. 부하 분산이 용이해 결함 감내가 쉬움 |

- 사용 중인 장비와 스케일 업 장비의 가격 차가 크면 스케일 아웃이 더 경제적일 수 있음.
> **오토스케일링**: 티켓팅·수강신청처럼 특정 시점에 트래픽이 급증하는 상황에 대비해, 필요할 때마다 시스템을 동적으로 확장·축소할 수 있는 기능을 **오토스케일링(auto scaling)** 이라고 함. 클라우드 서비스 업체 대부분이 제공함.

### Nginx로 알아보는 로드 밸런싱

**Nginx**는 대표적인 웹 서버 프로그램으로, 포워드 프록시/리버스 프록시 기능도 제공함. 설치 후 간단한 설정으로 콘텐츠 캐싱, 접근 제한, 로드 밸런싱 등이 가능함.

**Nginx 설정 관련 중요 3가지** (`$nginx`는 대부분 `/etc/nginx/` 경로)

- 모든 설정의 시작점인 `$nginx/nginx.conf` 파일
- 로그가 저장되는 `/var/log/nginx/` 디렉터리
- 각종 설정 파일이 포함되는 `$nginx/conf.d/` 디렉터리

`$nginx/conf.d/<파일명>.conf`에 로드 밸런싱 설정 파일을 작성함 (확장자는 `conf`).

```
upstream backend {
    server 10.10.10.2:80 weight=1;
    server 10.10.10.3:80 weight=2;
    server 10.10.10.4:80 backup;
}

server {
    listen 80;
    server_name localhost;
    location / {
        proxy_pass http://backend;
    }
}
```

- `server` 블록: 서버 이름(`server_name`)을 localhost로 하고, 80번 포트를 LISTEN 상태로 대기
- `location /`: 경로 `/`에 대한 HTTP 요청을 `proxy_pass`로 `backend` 서버 그룹에 넘김.
- `weight`: 가중치(기본값 1, 생략 가능) / `backup`: 두 서버에 문제가 발생해 연결이 불가능할 때 사용할 서버
- 위 설정대로면 `10.10.10.3`이 `10.10.10.2`보다 두 배 많은 트래픽을 받고, 두 서버에 문제가 생기면 `10.10.10.4`가 동작함.

로드 밸런싱 알고리즘을 지정할 수도 있음. 미명시 시 기본은 **라운드 로빈**임.

```
upstream backend {
    least_conn;   # 로드 밸런싱 알고리즘
    server 10.10.10.2:80 weight=1;
    server 10.10.10.3:80 weight=2;
    server 10.10.10.4:80 backup;
}
```

| 알고리즘 지시어 | 설명 |
|---|---|
| **least_conn** | 연결 수가 가장 적은 서버로 요청 전달 |
| **random** | 단순히 임의로 선택 |
| **ip_hash** | IP 주소 기반의 해시 활용 |

> **업스트림/다운스트림과 인바운드/아웃바운드**
> - **업스트림(upstream)**: 상위 서버로 데이터를 보내는 방향. 클라이언트 → 오리진 서버 트래픽
> - **다운스트림(downstream)**: 상위 서버에서 클라이언트로 데이터를 보내는 방향. 오리진 서버 → 클라이언트 트래픽
> - **인바운드(inbound)**: 네트워크 외부에서 내부로 들어오는 트래픽 (외부 사용자가 회사 웹사이트에 접속)
> - **아웃바운드(outbound)**: 내부 네트워크에서 외부로 나가는 트래픽 (회사 직원이 외부 웹사이트 방문)
