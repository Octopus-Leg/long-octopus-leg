## 5. 응용 계층 - HTTP의 기초

### DNS와 URI/URL

#### 도메인 네임과 DNS

**도메인 네임(domain name)** 은 `www.example.com`처럼 문자열 형태의 호스트 특정 정보로, 특정 IP 주소와 대응됨. IP 주소보다 기억이 쉽고, IP 주소가 바뀌어도 다시 대응하면 되므로 간편함.

- 도메인 네임과 IP 주소는 **네임 서버(name server, DNS 서버)** 에서 관리됨. 여러 개가 전 세계에 분산됨.
- IP 주소를 모르는 상태에서 도메인 네임에 대응되는 IP 주소를 알아내는 과정을 **리졸빙(resolving)** 이라고 함.

**도메인 네임의 계층적 구조 (점 기준)**

- 최상단에 **루트 도메인(root domain)**, 그 다음 **최상위 도메인(TLD, Top-Level Domain)** (예: com, net, org, kr, jp)
- 하위로 **2단계 도메인(세컨드 레벨 도메인)**, 3단계 도메인... 일반적으로 3~5단계
- `www.example.com.`처럼 도메인 네임을 모두 포함하는 것을 **전체 주소 도메인 네임(FQDN, Fully Qualified Domain Name)** 이라고 함.

네임 서버도 계층적 형태를 이루며, 분산되어 관리됨. 이 관리 체계를 **DNS(Domain Name System)** 라고 함.

**리졸빙 과정**

- 호스트는 가장 먼저 **로컬 네임 서버**에 질의함. 많은 경우 ISP가 로컬 네임 서버 주소를 자동 할당함. (공개 DNS 서버로 구글 `8.8.8.8`, 클라우드플레어 `1.1.1.1` 등 사용 가능)
- 로컬 네임 서버가 IP 주소를 모르면 **루트 네임 서버 → TLD 네임 서버 → 하위 네임 서버** 순으로 질의해 알아냄.

> **DNS 캐시**: 질의 과정이 너무 반복되면 트래픽이 많아지고 리졸빙이 느려지므로, 네임 서버들이 응답받은 결과를 임시 저장했다가 재활용함. 캐시된 값은 TTL(캐시될 수 있는 시간)이 정해져 있음.

#### DNS 레코드 타입

IP 주소에 도메인 네임을 대응하려면 네임 서버에 **DNS 자원 레코드(resource record, DNS 레코드)** 를 추가해야 함. 모든 레코드에는 **이름(Record Name)**, **값(Value)**, **레코드 타입(record type)** 이 있음.

| 레코드 타입 | 의미 |
|---|---|
| **A** | 도메인 네임과 IPv4 주소의 대응 관계 |
| **AAAA** | 도메인 네임과 IPv6 주소의 대응 관계 |
| **CNAME** | 도메인 네임에 대한 별칭 지정 |
| **NS** | 특정 호스트의 IP 주소를 알 수 있는 네임 서버 |
| **MX** | 해당 도메인과 연동된 메일 서버 |

#### 자원과 URI/URL

- **자원(resource)** 이란 네트워크 상의 메시지를 통해 주고받는 최종 대상을 의미함 (HTML/이미지/동영상/텍스트 파일 등).
- **URI(Uniform Resource Identifier)** 는 웹 상에서의 자원을 식별하기 위한 정보임.

| 방식 | 설명 |
|---|---|
| **URN(Uniform Resource Name)** | 이름 기반 식별 (예: `urn:isbn:0451450523`). 위치와 무관하게 식별 가능 |
| **URL(Uniform Resource Locator)** | 위치 기반 식별. 오늘날 더 많이 사용됨 |

**URL 구조** (예: `foo://www.example.com:8042/over/there?name=ferret#nose`)

| 요소 | 설명 |
|---|---|
| **scheme** | 자원에 접근하는 방법. 주로 프로토콜 (`http://`, `https://`) |
| **authority** | 호스트를 특정하는 IP 주소나 도메인 네임. 뒤에 포트 번호 명시 가능 |
| **path** | 자원이 위치한 경로. 슬래시(/) 기준 계층 표현 |
| **query** | URL 매개변수 역할의 문자열(쿼리 문자열). 물음표(?)로 시작, 앰퍼샌드(&)로 연결 |
| **fragment** | 자원의 일부분을 가리키는 정보. 주로 HTML 문서의 특정 부분 지정 |

### HTTP의 특징과 메시지 구조

**HTTP**의 목적은 애플리케이션의 다양한 자원을 네트워크를 통해 송수신하는 것임. 데이터 형식에 구애받지 않고 다양한 애플리케이션 데이터의 송수신을 가능하게 함.

#### HTTP의 특징

| 특징 | 설명 |
|---|---|
| **① 요청 응답 기반 프로토콜** | 요청 메시지를 보내는 클라이언트와 응답 메시지를 보내는 서버가 HTTP 요청/응답 메시지를 주고받음 |
| **② 미디어 독립적 프로토콜** | HTML, JPEG, PNG, JSON, XML, PDF 등 다양한 자원을 주고받을 수 있음. 자원의 종류를 **미디어 타입(media type, MIME 타입)** 이라고 함 |
| **③ 스테이트리스 프로토콜** | 상태를 유지하지 않음. 모든 요청을 독립적으로 간주. 확장성/견고성을 위한 설계 |
| **④ 지속 연결 프로토콜** | 하나의 TCP 연결에서 여러 요청-응답을 주고받는 기술(**킵 얼라이브, keep-alive**) 지원 |

- 미디어 타입은 '타입/서브타입' 형식임 (예: `text/html`, `image/png`, `application/json`, `text/plain`, `application/octet-stream` 등). 별표(`*`)는 통칭, 매개변수는 `type/subtype;charset=UTF-8` 형식으로 추가
- 스테이트리스: 서버가 많은 클라이언트의 상태를 유지하는 것은 큰 부담이며, 상태를 유지하지 않으면 특정 클라이언트가 특정 서버에 종속되지 않아 서버 추가/대체가 쉬워짐.
- 지속 연결: 초기 HTTP(1.0 이하)는 요청-응답마다 연결을 수립·종료하는 '비지속 연결'이었으나, HTTP 1.1 이상은 지속 연결을 제공함.

**HTTP 버전별 특징**

| 버전 | 특징 |
|---|---|
| **HTTP 1.1** | 현재까지 널리 사용. 지속 연결이 공식 지원됨. 메시지를 평문으로 전송. 콘텐츠 협상 등 편의 기능 추가 |
| **HTTP 2.0** | 바이너리 데이터 기반 송수신, 헤더 압축, 서버 푸시(server push), 멀티플렉싱(multiplexing) 기법으로 HOL 블로킹(Head-Of-Line blocking) 완화 |
| **HTTP 3.0** | UDP 기반 **QUIC(Quick UDP Internet Connections)** 프로토콜로 동작. TCP보다 빨라 성능 개선 |

> **HOL 블로킹**: 같은 큐에 대기하며 순차적으로 처리되는 여러 패킷이 있을 때, 첫 번째 패킷의 처리 지연으로 나머지 패킷의 처리도 모두 지연되는 문제 상황을 의미함.

#### HTTP 메시지 구조

HTTP 메시지는 **시작 라인**, **필드 라인**(0개 이상), **메시지 본문**(선택적)으로 이루어짐.

- 시작 라인은 요청 메시지면 **요청 라인**, 응답 메시지면 **상태 라인**이 됨.

```
요청 라인 = 메서드 (공백) 요청 대상 (공백) HTTP 버전 (줄바꿈)
상태 라인 = HTTP 버전 (공백) 상태 코드 (공백) 이유 구문 (줄바꿈)
```

| 필드 | 설명 |
|---|---|
| **메서드(method)** | 클라이언트가 서버의 자원에 대해 수행할 작업의 종류 |
| **요청 대상(request-target)** | 요청을 보낼 서버의 경로. 주로 쿼리 문자열이 포함된 경로 |
| **HTTP 버전(HTTP-version)** | 사용된 HTTP 버전 (`HTTP/1.1`) |
| **상태 코드(status code)** | 요청 결과를 나타내는 3자리 정수 |
| **이유 구문(reason phrase)** | 상태 코드에 대한 문자열 설명 (예: `HTTP/1.1 200 OK`, `HTTP/1.1 404 Not Found`) |

- 필드 라인에는 **HTTP 헤더**가 명시됨. 콜론(:)을 기준으로 **헤더 이름**과 **헤더 값**으로 구성됨

### HTTP 메서드와 상태 코드

#### HTTP 메서드

자주 사용되는 중요 메서드: GET, HEAD, POST, PUT, PATCH, DELETE

| 메서드 | 설명 |
|---|---|
| **GET** | 자원을 조회(획득)하기 위한 메서드 |
| **HEAD** | GET과 동일하나, 헤더만을 응답받는 메서드 (본문 미포함) |
| **POST** | 서버로 하여금 특정 작업을 처리하게끔 하는 메서드. 주로 새로운 자원 생성 |
| **PUT** | 자원을 대체(덮어쓰기)하기 위한 메서드 |
| **PATCH** | 자원에 대한 부분적 수정을 위한 메서드 |
| **DELETE** | 자원을 삭제하기 위한 메서드 |
| **CONNECT** | 자원에 대한 양방향 연결을 시작 |
| **OPTIONS** | 사용 가능한 메서드 등 통신 옵션 확인 |
| **TRACE** | 자원에 대한 루프백 테스트 수행 |

- PUT은 '대체', PATCH는 '부분적 수정'이라는 차이가 있음.
- 같은 URI에 대해 어떤 메서드에 어떻게 동작하는지 설계하는 것은 개발자의 몫임.

#### HTTP 상태 코드

상태 코드는 백의 자릿수를 기준으로 유형을 나눔.

| 범위 | 유형 |
|---|---|
| 100번대 | 정보성 상태 코드 |
| 200번대 | 성공 상태 코드 |
| 300번대 | 리다이렉션 상태 코드 |
| 400번대 | 클라이언트 에러 상태 코드 |
| 500번대 | 서버 에러 상태 코드 |

**200번대: 성공**

| 코드 | 이유 구문 | 의미 |
|---|---|---|
| 200 | OK | 요청이 성공함 |
| 201 | Created | 요청이 성공했으며 새로운 자원이 생성됨 |
| 202 | Accepted | 요청을 받았으나 아직 작업을 끝내지 않음 |
| 204 | No Content | 요청 성공했지만 본문으로 표시할 데이터가 없음 |

**300번대: 리다이렉션** (클라이언트가 요청한 자원이 다른 곳에 있을 때 요청을 이동시킴. 서버는 Location 헤더로 위치 안내)

| 코드 | 이유 구문 | 의미 |
|---|---|---|
| 301 | Moved Permanently | 영구적 리다이렉션 - 재요청 메서드가 변경될 수 있음 |
| 308 | Permanent Redirect | 영구적 리다이렉션 - 재요청 메서드가 변경되지 않음 |
| 302 | Found | 일시적 리다이렉션 - 재요청 메서드가 변경될 수 있음 |
| 303 | See Other | 일시적 리다이렉션 - 재요청 메서드가 GET으로 변경됨 |
| 307 | Temporary Redirect | 일시적 리다이렉션 - 재요청 메서드가 변경되지 않음 |
| 304 | Not Modified | 캐시 - 자원이 변경되지 않음 |

- 영구적 리다이렉션은 기존 URL을 기억할 필요가 없지만, 일시적 리다이렉션은 기존 URL을 기억해야 함.
- 308은 301의 애매모호함(GET으로 변경될 가능성)을 보완한 상태 코드임.

**400번대: 클라이언트 에러**

| 코드 | 이유 구문 | 의미 |
|---|---|---|
| 400 | Bad Request | 요청 메시지의 내용이나 형식 자체에 문제 |
| 401 | Unauthorized | 요청한 자원에 대한 유효한 **인증**이 없음 |
| 403 | Forbidden | 요청이 거부됨. 자원에 대한 접근 **권한**이 충분하지 않음 |
| 404 | Not Found | 요청받은 자원을 찾을 수 없음 |
| 405 | Method Not Allowed | 요청한 메서드를 지원하지 않음 |

- **인증(Authentication)**: 자신이 누구인지를 증명하는 작업 / **권한(Authorization, 인가)**: 인증된 주체에게 허용된 작업. 인증되었더라도 권한은 충분하지 않을 수 있음.

**500번대: 서버 에러**

| 코드 | 이유 구문 | 의미 |
|---|---|---|
| 500 | Internal Server Error | 요청을 처리할 수 없음 (서버 문제를 통칭) |
| 502 | Bad Gateway | 중간 서버가 잘못된 응답을 받았을 때의 통신 오류 |

### HTTP 주요 헤더

빈번히 사용되는 헤더의 의미를 기억해 두고, 새로운 헤더는 그때그때 정리해도 무방함.

#### 요청 메시지에서 주로 활용되는 헤더

| 헤더 | 설명 |
|---|---|
| **Host** | 요청을 보낼 호스트. 도메인 네임/IP 주소로 표현. 요청 라인과 조합하면 전체 URL을 알 수 있음 |
| **User-Agent** | 요청을 보낸 클라이언트의 프로그램 정보(브라우저 종류, 운영체제·아키텍처, 렌더링 엔진 등) |
| **Referer** | 클라이언트가 요청을 보낼 때 머무르던 URL. 유입 경로 파악에 사용 (`Referrer`가 아닌 오타 표기가 관용적으로 사용됨) |

#### 응답 메시지에서 주로 활용되는 헤더

| 헤더 | 설명 |
|---|---|
| **Server** | 응답 메시지를 보내는 서버 호스트 관련 정보 (예: `Apache/2.4.1 (Unix)`) |
| **Allow** | 처리 가능한 메서드 목록. 주로 405(Method Not Allowed)와 함께 사용 |
| **Location** | 자원의 위치 안내. 리다이렉션이나 새 자원 생성 시 사용 |

#### 요청과 응답 모두에서 활용되는 헤더

| 헤더 | 설명 |
|---|---|
| **Date** | 메시지가 생성된 날짜와 시각 |
| **Content-Length** | 메시지 본문의 바이트 단위 크기 |
| **Content-Type** | 메시지 본문에서 사용된 미디어 타입 |
| **Content-Language** | 메시지 본문의 자연어. 언어 태그(하이픈으로 서브 태그 구분, 예: `ko-KR`, `en-US`, `en-GB`) |
| **Content-Encoding** | 본문의 압축/변환 방식 (`gzip`, `compress`, `deflate`, `br` 등. 여러 번이면 순서대로 명시) |
| **Connection** | 원하는 연결 방식 (`keep-alive` 지속 연결, `close` 연결 종료) |

- Content-Type, Content-Language, Content-Encoding은 본문이 어떻게 '표현'되었는지와 관련되어 **표현 헤더(representation header)** 라고도 부름
